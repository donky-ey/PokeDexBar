# SP1 — 업스트림 사용량 조사·폴링 수정 포팅 (설계)

2026-10-08 · 업스트림 포팅 로드맵(SP1→SP2→SP3)의 첫 하위 프로젝트. 사용자와 범위 확정:
신규 프로바이더 제외, 기존 소스(Claude·Codex·Gemini·Grok·Cursor 로컬)의 정확도·폴링 수정만.

## 배경

포크는 2026-08-04(`23c8148`, upstream #139)에서 갈라졌고 이후 업스트림(chattymin/PokeTokenBar)
에 180커밋이 쌓였다. 양쪽 다 Core 를 많이 고쳐(포크 92·업스트림 128커밋) 머지는 불가능하며,
**기능 단위 재구현 포팅**으로 간다. 디렉터리 개명(`Sources/PokeTokenBar` → `Sources/PokeDexBar`,
`Tests/PokeTokenBarTests` → `Tests/PokeDexBarTests`) 외 내부 구조는 같다.

## 포팅 방식

1. 커밋당 한 사이클: `git show <c> | sed 's|PokeTokenBar|PokeDexBar|g' | git apply` 로 기계 적용을
   먼저 시도(3-way 불가 — 베이스 blob 이 다름), 리젝트 나는 헝크만 수동 이식. **적용 전에 업스트림
   커밋의 전체 diff 를 읽는다** — 부분 이해로 패턴을 베끼지 않는다(디버깅 스킬 규율).
2. 테스트 선행: 업스트림 커밋에 딸린 테스트를 먼저 이식해 **실패를 확인**한 뒤 구현을 적용한다
   (TDD 의 RED 를 업스트림 테스트로 대신 — 픽스처가 업스트림 실사용 검증을 거친 것이라
   "내 픽스처는 증거가 아니다" 규칙도 충족). 업스트림에 테스트가 없는 항목은 포크에서 작성.
3. 커밋 메시지는 영어, 원 커밋 참조를 남긴다: `fix: ... (upstream #NNN)`.
4. 항목 16개를 **4개 배치**로 나눠 배치마다 전체 스위트 + 커밋: ⓐ Codex 리더 계열(1·4·6·7·11)
   ⓑ 경계·탐지(2·3·5·8·14) ⓒ 폴링·갱신(9·15·16) ⓓ 로그·clamp(10·12·13).
   배치 ⓐ가 가장 크고 위험하므로 먼저 — 실패하면 뒤 배치는 영향 없이 중단 가능.
5. 충돌 주의점: 포크 Core 에는 게임 코드(PokeAPIClient 등)가 같이 살지만 이번 16건이 닿는 파일은
   사용량 전용(UsageStore·LocalUsageReader·LocalUsageCache·BinaryLocator·CodexRateLimitsProvider·
   LocalAdditionalUsageProvider·ModelPricing·AppLog·Models·UsageProvider)이라 게임과 안 겹친다.
   단 포크 고유 수정(예: 캐시읽기 clamp, CLAUDE.md 의 키체인 규율)과 의미가 겹치면 **포크 규율이
   우선** — 업스트림 헝크가 키체인 접근·메뉴바 규율을 건드리면 그 헝크는 버린다.

## 검증

- 배치마다: 전체 `swift test` + 이식한 업스트림 테스트 통과.
- 완료 후 실측: Dev 빌드 교체 → 로그에서 ① Codex 사용량이 기존과 동일하게 집계되는지(회귀 없음,
  #137 대개편 뒤 오늘 합계 비교) ② `codex limits skipped: binary not found` 가 ChatGPT.app 설치
  기기에서 사라지는지 ③ 로그 반복 억제가 동작하는지.
- 숫자 회귀 가드: #137 적용 전후로 같은 로컬 로그에 대한 오늘/주/월 합계를 비교하는 일회성 검증
  (dedup 강화로 합계가 **줄어들 수는** 있다 — 중복 제거가 목적이므로 감소는 정상, 증가는 결함).
